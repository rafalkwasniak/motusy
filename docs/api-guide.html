Motusy API — przewodnik

Jak rozmawiać z API aplikacji dla motocyklistów. Pisany ręcznie, po ludzku. Formalny kontrakt (OpenAPI) żyje osobno pod /docs/api.

Podstawy

Adres bazowyhttps://motusy.top/api/v1
FormatJSON w obie strony
NagłówkiAccept: application/json
Content-Type: application/json
UwierzytelnianieAuthorization: Bearer <token>
Językpolski — komunikaty przychodzą gotowe do pokazania użytkownikowi
Nagłówek Accept wysyłaj zawsze. API i tak odpowie JSON-em na całej ścieżce /api/, ale to jest zabezpieczenie po naszej stronie, nie zaproszenie do pomijania nagłówka.

Kształt odpowiedzi

Każda odpowiedź, sukces czy błąd, ma tę samą kopertę. Różni się tylko zawartością.

Sukces

{
  "success": true,
  "message": "Profil został zapisany.",
  "data": { ... }
}

Błąd

{
  "success": false,
  "code": "VALIDATION_ERROR",
  "message": "Podane dane są nieprawidłowe.",
  "errors": {
    "gender": ["Wybrana wartość pola płeć jest nieprawidłowa."]
  }
}
Rozgałęziaj logikę na code, nigdy na message. code jest stały. message jest tłumaczony i może się zmienić przy dowolnej poprawce językowej — warunek oparty na jego treści pęknie po cichu.

Zasady, na których możesz polegać

  • data pojawia się tylko wtedy, gdy jest co zwrócić.
  • Listy zawsze zwracają data: [], nawet puste — nie musisz rozróżniać „brak klucza” od „brak wyników”.
  • errors występuje wyłącznie przy błędach walidacji, z podziałem na pola.
  • Kody HTTP są prawidłowe: 200, 201, 401, 422, 429.

Kody błędów

KodHTTPCo zrobić w aplikacji
VALIDATION_ERROR422Pokaż błędy przy polach formularza — masz je w errors
INVALID_CREDENTIALS401Zostaw użytkownika na logowaniu, pokaż błąd
UNAUTHENTICATED401Token wygasł lub go nie ma — wyczyść i wróć na ekran logowania
TOO_MANY_REQUESTS429Za dużo prób, poproś o chwilę przerwy
PROFILE_REQUIRED409Najpierw zapisz profil, potem wyślij zdjęcie
MOTORCYCLE_REQUIRED409Najpierw zapisz motocykl, potem jego zdjęcie

INVALID_CREDENTIALS i UNAUTHENTICATED to nie to samo, choć oba zwracają 401. Pierwszy znaczy „złe hasło” i użytkownik zostaje na formularzu. Drugi znaczy „nie jesteś zalogowany” i trzeba go wylogować. Potraktowanie ich jednakowo daje albo wylogowywanie przy literówce w haśle, albo zapętlony ekran z martwym tokenem.

Cała ścieżka użytkownika

  1. Rejestracja — e-mail i hasło. Konto działa od razu, dostajesz token.
  2. Profil — nick i płeć. Bez tego konto jest niekompletne.
  3. Motocykl — marka, model, rocznik, kolor.
  4. Po obu zapisach profile_complete zmienia się na true i można wpuścić użytkownika do aplikacji.

Logowanie kolejnym razem to po prostu /auth/login i ten sam token w nagłówku.

Endpointy

POST /auth/register

Zakłada konto. Zwraca token, więc po rejestracji nie musisz logować się osobno.

{
  "email": "rafal@example.com",
  "password": "tajne-haslo-123",
  "device_name": "telefon"
}

Odpowiedź 201, w data znajdziesz token i user.

device_name jest opcjonalne, ale warto je wysyłać — patrz sekcja o wylogowaniu. Hasło ma minimum 8 znaków.

POST /auth/login

{
  "email": "rafal@example.com",
  "password": "tajne-haslo-123",
  "device_name": "telefon"
}

Odpowiedź 200, ta sama struktura co przy rejestracji.

Nieznany e-mail i złe hasło dają identyczną odpowiedź. To celowe — inaczej można by sprawdzać, kto ma konto w aplikacji. Limit: 10 prób na minutę.

Konto zalogowanego użytkownika: profil, motocykl, ustawienia widoczności, incognito.

POST /auth/logout — wymaga tokena

Unieważnia tylko ten jeden token. Pozostałe urządzenia zostają zalogowane.

Dlatego warto wysyłać device_name przy logowaniu — dzięki temu tokeny da się rozróżnić, a wylogowanie na telefonie nie wyrzuca użytkownika z tabletu.

POST /profile — wymaga tokena

Tworzy profil albo aktualizuje istniejący. Wysyłasz cały formularz, nie musisz sprawdzać, czy profil już jest.

{
  "nickname": "Rafal",
  "gender": "male",
  "first_name": "Rafał",
  "last_name": "Kwaśniak",
  "bio": "Jeżdżę od 2009.",
  "phone": "600100200",
  "first_name_visible": false,
  "last_name_visible": false,
  "phone_visible": true,
  "email_visible": false
}

Wymagane są tylko nickname i gender. Reszta jest opcjonalna.

gender przyjmuje wyłącznie male, female, other. To kody techniczne — etykiety („Mężczyzna”, „Kobieta”) budujesz w aplikacji.

POST /motorcycle — wymaga tokena

{
  "brand": "Yamaha",
  "model": "MT-07",
  "production_year": 2021,
  "color": "czarny",
  "description": "Po serwisie."
}

Wszystko poza description jest wymagane. Rocznik od 1900 do przyszłego roku. W MVP jedno konto to jeden motocykl.

Oba zapisy zwracają pełne konto, dokładnie w tej samej postaci co /auth/me. Nie musisz po zapisie wołać /auth/me, żeby odświeżyć ekran — masz świeże dane od razu.

POST /profile/incognito — wymaga tokena

Włącza i wyłącza tryb niewidzialny. Jedno pole, żadnych warunków wstępnych. Też zwraca pełne konto.

{
  "incognito": true
}

Osobny endpoint, bo POST /profile wymaga nicka i płci — przełącznik w ustawieniach musiałby wtedy wysyłać cały formularz i nie zadziałałby u kogoś, kto nie skończył onboardingu.

Incognito działa tak, jakbyś nie miał aplikacji. Nie jesteś wykrywany i sam nie wykrywasz — should_broadcast i should_scan lecą na false, a zgłoszenia spotkań z udziałem takiej osoby wracają ze statusem incognito. Historia sprzed włączenia trybu zostaje nietknięta. Jedyny zaplanowany wyjątek to awarie: gdy dojdą, będą przebijać ten tryb w obie strony, żeby prywatność nie kosztowała nikogo pomocy na drodze.

Zdjęcia

POST /profile/avatar — wymaga tokena

Wysyłasz jako multipart/form-data, pole nazywa się avatar. Nie JSON.

Przyjmujemy JPEG, PNG i WEBP, do 5 MB. Nowe zdjęcie zastępuje poprzednie, stary plik jest kasowany z dysku.

Zwraca pełne konto — w data.avatar masz gotowy adres do wyświetlenia.

DELETE /profile/avatar — wymaga tokena

Usuwa zdjęcie profilowe. Po tym data.avatar jest null.

POST /motorcycle/photo — wymaga tokena

To samo dla zdjęcia motocykla, pole nazywa się photo. Adres wraca w data.motorcycle.photo.

DELETE /motorcycle/photo — wymaga tokena

Usuwa zdjęcie motocykla.

Zdjęcia są przetwarzane po stronie API — nie musisz nic zmniejszać w aplikacji. Wysyłasz oryginał prosto z aparatu, a API sam skaluje, konwertuje do WEBP i czyści metadane. Avatar mieści się w 600 px, zdjęcie motocykla w 1200 px na dłuższym boku. Proporcje zostają, a zdjęcia mniejsze od limitu nie są powiększane. Przykład z produkcji: plik 1320 KB o wymiarach 3000×2000 wyszedł jako 29 KB (avatar) i 170 KB (motocykl).
Metadane EXIF są usuwane. Zdjęcia z telefonu niosą w sobie współrzędne GPS miejsca, w którym powstały — bez tego czyszczenia użytkownik, który sfotografował motocykl przed domem, udostępniałby wszystkim swój adres. Przy okazji API prostuje orientację, więc zdjęcia robione pionowo nie wychodzą obrócone.
Kolejność ma znaczenie. Zdjęcie doczepia się do istniejącego profilu albo motocykla. Wysłanie avatara przed zapisaniem profilu zwróci 409 z kodem PROFILE_REQUIRED — to nie błąd aplikacji, tylko informacja, że najpierw trzeba zapisać formularz.
Adresy zdjęć są absolutne, na przykład https://motusy.top/storage/avatars/2b3949cd-....png. Wstawiasz je wprost do komponentu obrazka, bez sklejania z niczym. Gdy zdjęcia nie ma, pole jest null.

Tożsamość BLE

GET /ble/identity — wymaga tokena

Zwraca komplet danych, których telefon potrzebuje do rozgłaszania i skanowania.

{
  "token": "aca75088d1a96c3dfe6a3df2a9a8182f",
  "service_uuid": "F8B8DA1E-F688-4478-B617-91C9BA4B33C5",
  "characteristic_uuid": "4438009D-8D2B-4C37-8FF5-E6270D88EB17",
  "refresh_after": "2026-08-14T19:06:52+00:00",
  "should_broadcast": true,
  "should_scan": true
}

Token ma 32 znaki szesnastkowe, czyli 128 bitów. Odczytywany jest przez połączenie, a nie z ramki rozgłoszeniowej, więc jego długość nie jest niczym ograniczona od góry.

Dwa różne identyfikatory — nie pomyl ich. service_uuid jest jeden dla całej aplikacji, stały i publiczny: leci w rozgłoszeniu i mówi tylko tyle, że w pobliżu jest ktoś z Motusy. Nie zdradza kto. token jest jeden na użytkownika, rotuje i siedzi w charakterystyce GATT — trzeba się połączyć, żeby go odczytać. Tożsamość ujawnia się więc dopiero komuś, kto faktycznie był obok.
Oba UUID-y zapisz lokalnie i miej zaszyte w kodzie jako awaryjne. Skanowanie musi działać bez zasięgu, a telefon w trasie bywa bez sieci. Pobierz je przy pierwszym udanym wywołaniu i używaj zapamiętanych. Zwracamy je z API po to, żeby dało się je zmienić bez wydawania nowej wersji aplikacji — a nie po to, żeby pytać przed każdym startem skanowania.
Token sam się zmienia — pytaj o niego regularnie. Endpoint podmienia go, gdy poprzedni się zestarzeje, więc aplikacja może wołać go przy każdym starcie i zawsze dostanie właściwą wartość. Pole refresh_after mówi, kiedy najwcześniej warto zapytać ponownie. Nie zapisuj tokena na stałe.
Po co rotacja. Gdyby identyfikator był stały, telefon rozgłaszałby przez całe życie konta tę samą wartość — ktoś ze zwykłym skanerem BLE mógłby bez aplikacji i bez zgody logować, kiedy konkretny motocyklista przejeżdża obok. Rotacja zamyka to okno. Stary token pozostaje rozpoznawalny jeszcze przez pewien czas, żeby spotkania zapisane bez zasięgu i wysłane później nadal dało się rozpoznać.

POST /ble/identity/rotate — wymaga tokena

Wymusza natychmiastową zmianę identyfikatora. To gotowa funkcja „zresetuj moją tożsamość" dla użytkownika, który czuje się śledzony.

Czytaj should_broadcast i should_scan z odpowiedzi, nie wyliczaj ich z incognito. Dziś oba są po prostu zaprzeczeniem trybu incognito, ale gdy dojdą awarie, użytkownik z aktywną awarią będzie musiał rozgłaszać mimo trybu niewidzialnego. Jeśli aplikacja czyta gotowe flagi, zmienimy tę regułę na serwerze i nie wymusi to wydania nowej wersji.

Urządzenia

POST /devices — wymaga tokena

{
  "device_id": "telefon-rafala",
  "platform": "android",
  "app_version": "1.0.0",
  "push_token": "fcm-abc"
}

Rejestruje urządzenie albo odświeża to, co o nim wiemy. Możesz wołać przy każdym starcie — to nadpisanie, nie tworzenie kolejnego wpisu.

platform przyjmuje ios albo android. push_token jest opcjonalny i na razie nieużywany, ale gdy dojdzie Firebase, będzie już na miejscu. Wyślij go ponownie, gdy się zmieni — Firebase je wymienia.

Zarejestruj urządzenie po każdym zalogowaniu. Rejestracja wiąże je z tokenem dostępowym, którego właśnie użyłeś. Dzięki temu da się później wylogować pojedyncze urządzenie i wysłać powiadomienie na konkretny telefon, a nie na całe konto.

Spotkania

Jedno zgłoszenie wystarczy — spotkanie zapisuje się obu stronom. Jeśli wykryjesz motocyklistę, a jego telefon nie wykryje Ciebie, spotkanie i tak powstaje i pojawia się w historii obojga. Wcześniej wymagaliśmy zgłoszenia z obu telefonów; ta reguła upadła, bo iPhone nadający w tle jest niewidoczny dla Androida, więc w parze iOS–Android wykrycie zawsze idzie tylko w jedną stronę i żadne takie spotkanie nigdy by się nie potwierdziło.

POST /meetings — wymaga tokena

Zgłasza motocyklistów wykrytych przez BLE. Przyjmuje tablicę, bo mijając grupę wykryjesz kilku naraz i to ma być jedno żądanie, nie pięć. Maksymalnie 20 na paczkę — przekroczenie to 422 na całą paczkę, więc dziel lokalnie przed wysyłką.

{
  "detections": [
    {
      "event_id": "wygenerowany-przez-aplikacje",
      "ble_token": "aca75088d1a96c3dfe6a3df2a9a8182f",
      "latitude": 50.4201,
      "longitude": 18.9273,
      "detected_at": "2026-08-13T18:42:15Z",
      "rssi": -67
    }
  ]
}

Wysyłasz token BLE, nie identyfikator użytkownika — telefon go nie zna i nie musi. Rozpoznaniem zajmuje się API.

Współrzędne to pozycja Twojego telefonu w chwili wykrycia, nie punkt pomiędzy wami. Każde zgłoszenie zachowuje własną. rssi jest opcjonalne i służy wyłącznie do strojenia progów odległości w przyszłości. detected_at wysyłaj w UTC ze strefą i stawiaj w chwili wykrycia, nie wysyłki.

Odpowiedź

Każde zgłoszenie dostaje własny wynik, w tej samej kolejności — odrzucenie jednego nic nie mówi o pozostałych.

Każdy status z tej tabeli znaczy „możesz skasować z kolejki". Ponawiaj wyłącznie przy błędzie sieci, 5xx i 429 — tam nic nie zostało zapisane.
Limit: 30 żądań na minutę na konto. Po przekroczeniu dostaniesz 429 z kodem TOO_MANY_REQUESTS i nagłówkiem Retry-After — użyj go zamiast zgadywać odstęp. Przy normalnej jeździe nie da się w ten limit uderzyć; telefon wracający po dobie bez zasięgu z dwustoma zaległymi wykryciami wyśle około dziesięciu żądań.
Powiadomienie możesz pokazać od razu. Gdy meeting jest wypełnione, masz w meeting.user nick i motocykl, czyli wszystko na „Spotkałeś Marka, Yamaha MT-07”.
event_id generuj sam i zapamiętaj. Jeśli wyślesz żądanie i nie doczekasz odpowiedzi, ponów je z tym samym event_id — nie powstanie drugi wpis, a odpowiedź będzie taka jak za pierwszym razem. Identyfikatory są liczone osobno dla każdego telefonu, więc to, że druga strona nadała swojemu zgłoszeniu inny, niczego nie psuje.
Nie wołaj API przy każdym skanie. BLE wykrywa tę samą osobę co kilka sekund. Trzymaj lokalnie listę już zgłoszonych i odezwij się raz. API i tak pilnuje karencji, ale nie po to, żeby aplikacja mogła go zalewać.
Karencja: 6 godzin na parę, liczone od momentu spotkania. Mijasz tego samego motocyklistę rano w drodze do pracy i dwie godziny później jadąc do urzędu — to jedno zdarzenie, nie dwa. Wspólna trasa też zostaje jednym wpisem. Dopiero po tym oknie kolejne minięcie jest nowym spotkaniem.

GET /meetings — wymaga tokena

Historia spotkań, od najnowszych. Stronicowana: ?page=1&per_page=20, maksymalnie 50.

Pusta historia zwraca data: [], nigdy braku klucza.

Historia to nie suma Twoich zgłoszeń. Znajdą się w niej spotkania, których Twój telefon nigdy nie zgłosił, bo zgłosiła je druga strona. Buduj widok z tego, co zwraca GET /meetings, a nie z własnej kolejki wysyłkowej.

GET /meetings/{id} — wymaga tokena

Szczegóły jednego spotkania — pod kliknięcie w powiadomienie albo w pozycję historii.

Czytelne dla obu uczestników i tylko dla nich. Cudze spotkanie zwraca 404, a nie 403, żeby nie dało się sprawdzać, które identyfikatory istnieją.

Obrazki

Adresy zdjęć są pełne i publiczne. data.avatar i data.motorcycle.photo zwracają gotowy adres — nie doklejaj do niego niczego i nie buduj go sam. Pliki nie wymagają tokena.
Katalog /storage/ zwraca Access-Control-Allow-Origin: *. Dzięki temu zdjęcia działają w podglądzie webowym, gdzie Flutter pobiera je żądaniem HTTP i podlegają one regułom CORS. Samo /api/ ma ten nagłówek niezależnie, z konfiguracji Laravela.

Widoczność danych

Użytkownik decyduje, które dane widzą inni. Flagi *_visible ustawiasz przy zapisie profilu.

Ważne dla aplikacji: ukryte pole nie znika z odpowiedzi — przychodzi jako null. Zestaw kluczy jest zawsze taki sam, niezależnie od tego, kto patrzy. Dzięki temu nie musisz sprawdzać, czy klucz w ogóle istnieje.

Własne dane widzisz zawsze w całości. Filtrowanie dotyczy tylko tego, co widzą inni.

Co to znaczy w praktyce dla FlutterFlow

Nie znam Twojej wersji edytora na tyle, żeby opisywać kliknięcia, ale niezależnie od wersji FlutterFlow zapyta o te same rzeczy. Poniżej to, co trzeba mu podać.

Ścieżki do wartości w odpowiedzi

Do wyciągania danych z JSON-a FlutterFlow używa notacji ze ścieżką. Najczęściej potrzebne:

Co chceszŚcieżka
Token po zalogowaniu$.data.token
Nick użytkownika$.data.user.nickname (po logowaniu)

Uwaga na różnicę. /auth/login i /auth/register pakują konto w data.user, bo obok leży data.token. Natomiast /auth/me, /profile i /motorcycle zwracają konto wprost w data. To najczęstsze miejsce na pomyłkę w ścieżce.

Token

Token nie wygasa sam z siebie — traci ważność dopiero przy wylogowaniu. Zapisz go w bezpiecznym magazynie urządzenia, nie w zwykłej zmiennej, i dokładaj do każdego chronionego żądania.

Kolejność przy pierwszym ekranie

  1. Masz zapisany token? Zawołaj /auth/me.
  2. Dostałeś 200 i profile_complete: true → ekran główny.
  3. Dostałeś 200, ale profile_complete: false → onboarding.
  4. Dostałeś 401 z UNAUTHENTICATED → wyczyść token, ekran logowania.

Żeby nie szukać na próżno — te rzeczy są zaplanowane, ale jeszcze nie istnieją:

  • obserwowanie, zaproszenia, znajomi,
  • statusy „Lecę na moto” i zgłoszenia awarii,
  • dashboard,
  • usuwanie konta,
  • powiadomienia push.
